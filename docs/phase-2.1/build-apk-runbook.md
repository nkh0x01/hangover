# Hangover Mobile — Android APK Build Runbook

> Phase 2.1 deliverable. End-to-end recipe for producing installable
> APKs of both the customer app and the driver app on a developer
> laptop or CI runner. Use the same recipe for the first real-device
> QA cycle.

## TL;DR

```bash
# one-time, after cloning
./mobile/scripts/setup-mobile-platforms.sh

# every build
./mobile/scripts/build-apk.sh dev          # both apps, dev flavor
./mobile/scripts/build-apk.sh staging      # both apps, staging flavor
./mobile/scripts/build-apk.sh prod customer
./mobile/scripts/build-apk.sh prod driver
```

APKs land in `build/customer-<flavor>.apk` and `build/driver-<flavor>.apk`
ready for `adb install`.

## Prerequisites

| Tool                   | Version             | Notes                                              |
|------------------------|---------------------|----------------------------------------------------|
| Flutter SDK            | 3.24+ stable channel | `flutter --version` should print `3.24.x` or later |
| Android Studio         | 2024.1 (Iguana)     | needed for SDK platform tools                       |
| Android SDK platform   | API 34              | min target for Play Store                           |
| Android NDK            | 26.3.x              | matches `ndkVersion` set by Flutter                 |
| Java                   | 17 (Temurin)        | `JAVA_HOME` exported                                |
| Melos                  | 6.x                 | `dart pub global activate melos`                    |
| Firebase CLI (optional)| latest              | only needed when regenerating `firebase_options.dart` |

Verify in one shot:

```bash
flutter doctor -v
melos --version
java -version
echo "$JAVA_HOME"
```

Resolve every red mark from `flutter doctor` before continuing — every
one of them will surface during `flutter build apk`.

## Workspace setup

```bash
git clone git@github.com:nkh0x01/hangover.git
cd hangover
melos bootstrap          # runs `flutter pub get` across the workspace
./mobile/scripts/setup-mobile-platforms.sh
```

`setup-mobile-platforms.sh` performs four operations per app:

1. `flutter create --platforms=android,ios --org app.hangover .`
   if `android/` or `ios/` is missing.
2. Overlays the production manifest, Gradle config, network-security
   config, ProGuard rules, splash drawable, notification icon, and
   colour palette from `mobile/templates/android/<app>/...`.
3. Drops the iOS Info.plist additions and entitlements next to the
   Xcode project (manual merge into `Info.plist` — Xcode rewrites the
   file on every build, so we never overlay it directly).
4. Re-runs `flutter pub get` so the generated `android/` is in sync with
   the workspace pubspec.

Running the script a second time refreshes the overlays without
clobbering anything that was generated by `flutter create`.

## Firebase setup (one-time per app)

The apps degrade gracefully to `NullPushService` when Firebase isn't
initialised, but real-device QA wants real push delivery.

1. Create a Firebase project (or reuse the existing `hangover-prod`).
2. Add two Android apps:
   - `app.hangover.customer.dev`  ← customer dev/QA
   - `app.hangover.driver.dev`    ← driver dev/QA
   - Repeat for `staging` and prod application ids if you intend to
     ship multiple Firebase projects per flavour.
3. Download each `google-services.json` and drop it at:
   ```
   mobile/apps/customer_app/android/app/google-services.json
   mobile/apps/driver_app/android/app/google-services.json
   ```
4. (iOS) `GoogleService-Info.plist` → `mobile/apps/<app>/ios/Runner/`.

The Android Gradle plugin (`com.google.gms.google-services`) is already
wired into both app modules — it picks up the JSON automatically.

If `google-services.json` is missing, the Gradle plugin fails the build
loudly. To produce an APK without Firebase (e.g. for the first
end-to-end smoke), comment out the plugin line in the app's
`android/app/build.gradle.kts`:

```kotlin
// id("com.google.gms.google-services")
```

…and accept that `FirebasePushService.initialize()` will fall through
to the null path.

## Signing — release keystore

For Play Store / TestFlight uploads you need an upload keystore.
Generate it **once** and store the `.jks` securely (Bitwarden, 1Password,
or your team's secrets manager — **never** commit it):

```bash
keytool -genkey -v \
  -keystore hangover-upload.jks \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -alias upload
```

Then for each app:

```bash
cp mobile/templates/android/shared/key.properties.example \
   mobile/apps/customer_app/android/key.properties
```

…and fill in the four fields. `storeFile` is resolved relative to
`mobile/apps/<app>/android/`, so the typical layout is:

```
mobile/apps/customer_app/android/
├── hangover-upload.jks         (gitignored)
├── key.properties              (gitignored)
└── app/build.gradle.kts
```

If `key.properties` is missing, the release build falls back to the
**debug** keystore — you'll get an installable APK that `adb install`s
fine on test devices but is not Play-Store-eligible.

## Maps API key

Both apps embed a Google Maps Android API key via `manifestPlaceholders`.

Set it before building:

```bash
export MAPS_API_KEY="AIza...your_android_key..."
./mobile/scripts/build-apk.sh dev
```

…or pass it as a Gradle property:

```bash
flutter build apk \
  --release --flavor=prod \
  --target=lib/main_prod.dart \
  --dart-define=MAPS_API_KEY=AIza... \
  -- -PMAPS_API_KEY=AIza...
```

Restrict the key to the package + SHA-1 fingerprint of the signing cert
in Google Cloud Console **before** producing the prod APK.

## Build commands

### Both apps, all flavours

```bash
./mobile/scripts/build-apk.sh dev
./mobile/scripts/build-apk.sh staging
./mobile/scripts/build-apk.sh prod
```

### One app, one flavour

```bash
./mobile/scripts/build-apk.sh prod customer
./mobile/scripts/build-apk.sh staging driver
```

### Raw Flutter (when you want full control)

```bash
cd mobile/apps/customer_app
flutter build apk \
  --release \
  --flavor=prod \
  --target=lib/main_prod.dart \
  --split-per-abi
```

`--split-per-abi` produces three APKs (arm64, armeabi-v7a, x86_64). For
QA we ship the **universal** APK (drop the flag) so the same artefact
installs on every device.

## Installing on a device

```bash
adb devices                            # confirm the device shows as `device`
adb install -r build/customer-dev.apk
adb install -r build/driver-dev.apk

# Watch logs from the customer app
adb logcat -s flutter:* AndroidRuntime:* "*:E"
```

For long-running QA sessions, pin the screen on (`adb shell svc power
stayon true`) and connect the device to wall power.

## Troubleshooting

### `Execution failed for task ':app:processProdReleaseGoogleServices'`
Missing `google-services.json` for the chosen flavour package id. Either
add it, or temporarily disable the Google Services Gradle plugin (see
"Firebase setup" above).

### `Keystore file not set for signing config release`
`key.properties` is missing — release will sign with the debug keystore
instead. To force a signed release, copy `key.properties.example` and
fill it in.

### `Cause: API key not found. Check that <meta-data android:name="com.google.android.geo.API_KEY"`
Maps API key wasn't piped through to `manifestPlaceholders`. Re-export
`MAPS_API_KEY` and rebuild.

### `R8: Missing class …`
A ProGuard rule is too aggressive. Add the missing class to
`mobile/templates/android/shared/proguard-rules.pro` — never disable
shrinking. Rebuild and re-run.

### `adb install` returns `INSTALL_FAILED_UPDATE_INCOMPATIBLE`
You're installing a debug APK over a release-signed one (or vice
versa). `adb uninstall app.hangover.customer.dev` first.

### "App not installed" on a Xiaomi / MIUI device
MIUI blocks installs from unknown sources by default. Enable
*Settings → Privacy → Special permissions → Install unknown apps → adb*
on the device.

## CI integration

`.github/workflows/mobile-build.yml` (lives in Phase 2.2) runs the same
recipe on every `main` push:

```yaml
- run: ./mobile/scripts/setup-mobile-platforms.sh
- run: ./mobile/scripts/build-apk.sh staging
- uses: actions/upload-artifact@v4
  with:
    name: hangover-staging-apks
    path: build/*.apk
```

Keystore + Firebase JSON come from `secrets/` and are written into
place at the start of the job.

## Output naming convention

```
build/customer-dev.apk          # 60–80 MB (dev, debug-signed)
build/customer-staging.apk      # 35–45 MB (R8 shrunk)
build/customer-prod.apk         # 35–45 MB (R8 shrunk + prod keystore)
build/driver-dev.apk
build/driver-staging.apk
build/driver-prod.apk
```

Per-ABI splits add `-arm64-v8a`, `-armeabi-v7a`, `-x86_64` suffixes.
